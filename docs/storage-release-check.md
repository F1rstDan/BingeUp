# 存档加固发布的身份与迁移规则

本文用于 `v0.0.1 → v0.0.2` 的本地安装升级和存档迁移检查。发布前必须同时满足身份不变、原目录升级和数据兼容三项要求。

## 1. 发布身份必须保持不变

- 产品名称保持“刷刷升级”。
- `package.json`、`package-lock.json` 与 `wxt.config.ts` 的 manifest 版本均对齐到 `0.0.2`。
- Chrome 与 Edge 分别使用各自构建产物。升级时继续加载原解压目录，不得移动目录或新建平行目录。
- 解压安装的扩展 ID 依赖原加载路径。覆盖文件并重新加载后，扩展 ID 必须与升级前一致。
- 不得在 manifest 中新增 `key`。不得先卸载扩展再安装新版本；卸载会清除 IndexedDB 与 `chrome.storage.local`。
- Release 压缩包先解压到临时位置，再覆盖原解压目录中的文件。不要删除原目录后重新加载。

## 2. 存档格式必须保持兼容

- IndexedDB 数据库名保持 `bingeup`，数据库版本保持 `2`。不得为发布重命名数据库或降低版本。
- 公共服务导出的备份格式保持 `version: 1`，并保持原有四个顶层字段。导出对象不得包含 `storageMeta`。
- 自动恢复快照必须兼容旧的实体 `version: 1` 与档案 `version: 2`。当前快照和上一代快照都可保留各自的数据库代次与修订信息。
- `storageMeta` 是存储控制记录，不属于用户数据。自动恢复判断只检查其余 7 个权威仓库。
- 除 `storageMeta` 外的 7 个权威仓库全为空时，才允许自动恢复。只有设置的快照也可恢复。
- 部分数据丢失或出现孤立引用时，扩展进入隔离并保留快照，不覆盖剩余设置或记录。已有新设置或数据时不回退到旧快照。
- 自动恢复快照位于扩展的 `chrome.storage.local`。它不跨设备同步，并会在卸载扩展时删除。

## 3. 迁移验证

以下测试是本次发布要求的存档迁移回归：

```bash
npx vitest run tests/unit/storage/database.test.ts tests/unit/storage/recovery-snapshot.test.ts tests/unit/storage/data-transfer.test.ts
```

- `database.test.ts` 验证数据库名与版本、v1 到 v2 的仓库升级、元数据记录和待备份确认。
- `recovery-snapshot.test.ts` 验证旧 v1 实体、v2 档案、当前与上一代快照、整库恢复、只有设置恢复和部分丢失隔离。
- `data-transfer.test.ts` 验证公共备份 v1 结构，确认导出使用一致只读事务且不暴露 `storageMeta`。

完整发布门禁仍为 `npm run check`。涉及构建的改动还需运行 `npm run build` 与 `npm run build:edge`。

## 同配置重启门禁

构建两种产物后，运行：

```bash
npm run test:storage:restart
```

命令分别启动 Chromium 和 Edge，各执行 5 次同配置关闭与重启。每次检查自报认识学习卡、扩展 ID、待备份标记和快照修订。然后只在测试配置中删除学习卡，确认部分丢失后进入隔离，保护健康快照并拒绝继续出题。

脚本只创建独立配置目录，不使用日常浏览器配置。结果与诊断截图写入 `docs/reports/storage-audit-2026-10-30/evidence/`，原始故障审计结果不被替换。缺少任一浏览器时，该检查失败，不应记为通过。

## 4. 原目录升级步骤

1. 升级前在设置页导出用户备份。
2. 在扩展管理页记录升级前的扩展 ID 与原解压目录绝对路径。
3. 构建或解压 `0.0.2`，用新文件覆盖原目录中的构建文件。保留原目录本身。
4. 在扩展管理页点击“重新加载”。不要点击“移除”，也不要加载另一个新目录。
5. 检查版本为 `0.0.2`、扩展 ID 未变化、IndexedDB 学习记录和设置仍可读取。
6. 检查自动快照诊断、待备份状态和手动导入流程。部分丢失状态必须显示隔离；完整空库才应触发自动恢复。

任何步骤要求卸载、重建数据库、移动原目录或新增 manifest `key` 时，应停止发布并调查。自动快照只提供本机同扩展身份的恢复能力，不能替代升级前的手动导出。
